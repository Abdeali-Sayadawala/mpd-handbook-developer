How My Property Doctors is built

A personal guide for you, written for someone who has not built web apps. It is only on this computer: it lives in D:\MPDv2\my-guide, outside every git repository, so it is never committed, pushed or published. Open index.html in a browser. Nothing here needs the internet.

1. The big picture in one minute

Everything you use online is built from the same three ingredients. A "website" and a "web app" use the same ones. The difference is how much they do.

IngredientWhat it isIn MPD
The screen (frontend)What runs in the visitor's browser: the pages, buttons and forms. Built from HTML (the structure), CSS (the looks) and JavaScript (the behaviour).mpd-global (the public site) and mpd-frontend (the portal and console), both made with Next.js
The brain (backend / API)A program on a server that holds the rules, checks who you are, and talks to the database. It never draws pages; it answers questions like "give me this worker's jobs" with data.mpd-backend, made with NestJS
The memory (database)Where everything is stored permanently: customers, properties, orders, jobs, photos' records.PostgreSQL, managed through Prisma
A good way to think about it: a restaurant. The dining room is the frontend (what guests see). The kitchen is the backend (where the real work and the rules are). The pantry is the database. Guests never walk into the kitchen; the waiter (the API) carries orders in and food out.

2. A normal website versus a web app

Technically there is no hard line. People use the words for how the thing behaves. Press the buttons to compare.

The honest summary

Website (like mpd-global)Web app (like mpd-frontend)
Who is it for?Anyone, no sign-inSigned-in people, each seeing different things
Does it change data?Almost never (maybe a contact form)Constantly: buying, approving, uploading, finishing jobs
Where do the rules live?Nowhere much; it is mostly contentIn the backend: who may do what, prices, status changes
Is each person's page different?No, everyone gets the same pageYes, built per person at the moment they ask
What can go wrong?A typo, a broken linkMoney, privacy, two people acting at once, someone seeing what they should not
So "making it a web app" is mostly not about the screen at all. It is the sign-in, the permissions, the data and the rules behind the screen. That is why most of the effort in MPD is in mpd-backend.

3. What happens when someone opens a page

Every visit is a conversation. Learn this once and everything else makes sense.

  1. You type an address or tap a link. The browser sends a request over the internet to a server.
  2. The server answers with HTML, CSS and JavaScript files. The browser draws the page from them.
  3. When you click something that needs data or changes something, the page sends another request, usually to an API, and gets back data (not a page). It then updates what you see.

Static page versus dynamic page

Static

The page is made ahead of time. The server just hands out the finished file. Fast, cheap, same for everyone. This is how mpd-global mostly works.

Dynamic

The server (or the browser) builds the page after asking "who is this, and what is theirs?". Different for each person. Every screen in mpd-frontend works this way (the route files say dynamic = 'force-dynamic').

4. The pieces of MPD and how they talk

The contract that keeps them honest

The backend publishes a file called openapi.json. It lists every question the API can answer, what to send and what comes back. The frontends run pnpm api:generate and get a typed client from it (src/api/schema.d.ts). If the backend changes something and the frontend still expects the old shape, the type check fails before anyone sees a broken screen. That is why our order is always: backend first, export the contract, regenerate, fix the frontend.

6. Inside the frontend (Next.js)

Next.js is a framework: a ready-made frame around React (a library for building screens out of reusable pieces). It decides how pages are named, how they are sent, and where code runs.

Folders and what they mean

WhereWhat lives there
app/Every folder here is a web address. app/admin/(console)/jobs/page.tsx is the page at /admin/jobs. A folder in brackets, like (console), only groups pages that share a layout; it does not appear in the address.
app/layout.tsx, AppShell.tsxThe frame around pages: the menu, top bar, the phone drawer
src/components/The screens' pieces: JobsBoard, ExtraWork, MyDay… Reused everywhere
src/actions/"Server actions": small functions that run on the server when a button is pressed. They hold the sign-in and call the API.
src/api/The generated client and types. Never edited by hand.
src/lib/Helpers: money formatting, the menu list (nav.ts), session cookies, call()
middleware.tsA guard that runs before every page: not signed in, go to login. (Only a convenience. The backend is the real lock.)
app/api/…A few special web addresses used for photo uploads, because server actions are too small for big files
public/Plain files like the logo and the app icons

Two kinds of code in one app

Runs on the server

Pages that fetch data, server actions, the middleware. It can hold secrets, read cookies, and talk to the backend. The visitor never sees this code.

Runs in the browser

Anything marked 'use client' at the top (like ExtraWork.tsx): things that react to clicks, hold form text, open dialogs. The visitor's device runs it.

How sign-in is kept

When someone logs in, the backend gives two tokens: a short-lived access token (a signed pass) and a longer refresh token. The frontend keeps them in cookies the browser's scripts cannot read (mpd_at, mpd_rt). Every server action goes through call() (src/lib/server-api.ts), which attaches the pass. If the pass has expired, call() trades the refresh token for a new one once and retries, so people are not thrown out mid-task.

Looks: Tailwind

Instead of one big stylesheet, small named classes sit on each element, like btn btn-primary !h-12 (a main button, 48 px tall). A few shared ones (btn, card, field-input) are defined in app/globals.css with the brand colours.

7. Inside the backend (NestJS)

NestJS is a framework that makes a backend tidy by giving every kind of code a fixed place.

PieceJobExample

PrismaThe translator between code and the database. prisma/schema.prisma describes every table.model JobExtra

TestA script that plays the app like a user (sign in as a worker, send a request, expect a refusal) to prove the rules hold.test/job-extras.e2e-spec.ts

The rules we never break

  • Money is whole paise (₹1 = 100) and is calculated on the server only. A browser can say anything; the server never trusts a price it was sent.
  • A status moves only through one gate. A job cannot jump from "requested" to "closed"; job-state.ts lists every allowed move and each is written to a history.
  • Two people for money. Someone records a payment, a different person approves it (the "maker and checker").
  • Another customer's record looks like it does not exist (404, not "forbidden"), so nobody can probe for what exists.
  • Codes and passwords are stored scrambled (hashed). Even we cannot read a customer's job code.
  • Races are handled in the database. "First provider to accept wins" is a single guarded update, not a hope.
  • Everything important is audited (who, what, when).
Why so careful? A web app handles real people's property and money. A website can survive being wrong; an app that handles payments cannot.

9. Who can see and do what

There are two locks, and only the second is real.

  1. The first lock is cosmetic. The frontend hides menu items a role should not use (roles in nav.ts) and the middleware sends strangers to login. It keeps screens tidy.
  2. The second lock is the backend. Every address checks your role and whether the record is yours (your organisation, your area, your job). Even if someone types an address by hand or edits the page in their browser, the backend still refuses.

Every role is tested for what it must be refused, not only for what it can do. That is the reason the test list is long.

10. How a change gets made, step by step

  1. Decide the rule in plain words (you did this for extra work).
  2. Database: describe new tables in schema.prisma, write the migration SQL.
  3. Backend: DTOs, service (the rules), controller (the address), module wiring.
  4. Tests: an end-to-end spec that plays every role, including the refusals.
  5. Export the contract: pnpm openapi:export, then in the frontend pnpm api:generate.
  6. Frontend: server actions, then the components and page, then npx tsc --noEmit and pnpm lint.
  7. Docs: progress file, specs, both handbooks, the role guide, every CLAUDE.md, and the context repo.
  8. Verify and push: verify.ps1 checks the numbers and that nothing is left uncommitted; then commit and push.
We never run pnpm build in the frontend while you run it, because both use the same working folder. Type checking and lint give the same safety without that clash.

11. Where it will run

For launch, one rented server (AWS Lightsail in Mumbai) runs everything in containers: a gatekeeper (Caddy), the API, the background worker, the web app and the database. Files go to private storage (S3) and emails through SES. The public site could later move to pure file hosting (S3 plus CloudFront) because it is static; the signed-in app needs a real server because of the sign-in and server actions. You decided to leave this until after launch. See 11-tech-explained.md in mpd-context for the longer answer.
