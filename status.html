Run it on a 16 GB Windows laptop

# one time
docker compose -f docker-compose.dev.yml up -d      # in mpd-backend: Postgres only
pnpm install                                        # in each repo
pnpm prisma migrate deploy && pnpm db:seed          # in mpd-backend (seed is safe to repeat)

# every day (three terminals)
mpd-backend   : pnpm dev          # API on :4000, Swagger at /docs
mpd-frontend  : pnpm dev          # console + portal on :3000
mpd-global    : pnpm dev -p 3001  # public website

# checks
mpd-backend   : pnpm lint && pnpm test:e2e && pnpm openapi:export
mpd-frontend  : pnpm api:generate && npx tsc --noEmit && pnpm lint
  • Dev admin: the email and password come from mpd-backend/.env (SEED_ADMIN_EMAIL, SEED_ADMIN_PASSWORD). Staff sign in at /admin/login, customers at /login.
  • Email is console-only. Invitation and OTP emails appear in the API terminal.
  • Change order: backend, then pnpm openapi:export, then pnpm api:generate in the apps, then fix type errors.
  • Windows gotchas: stop the API before prisma generate (the engine file is locked). Do not run pnpm build in the frontend while its dev server runs. prisma migrate dev refuses enum changes without a terminal, so write the SQL by hand and run migrate deploy.
  • Files uploaded in development go to mpd-backend/.storage/ (git-ignored).

Key flows

Vault upload

Multipart upload, file type read from the bytes (PDF, JPG, PNG, HEIC, DOCX), 20 MB, SHA-256 de-dup per folder, scan, stored under a generated key. A document can be locked (locked_reason) while KYC or an owner registration relies on it. Opening a file is a 5-minute signed token; sharing is a hashed token with expiry and a view limit. Every view is logged.

KYC

Customer uploads a scan to the KYC folder, then submits it with a number. Only a masked number is kept (Aadhaar: last 4 digits only; a full number is refused). Ops verify or reject with a reason. The customer is VERIFIED when any identity document is verified.

Owner registration

Project owner (set up by ops) creates a project and units, registers an owner with details and proof, submits. Ops approve (or the project skips review) and an invitation email goes out (single use, 14 days, hash stored). The invited person sets a password or signs in, becomes the registered owner, and gets a copy of the proof. A change of owner is always reviewed and keeps history.

Onboarding case

A website inquiry (POST /v1/public/inquiries) or a staff-made case starts a case, assigned to the franchise whose territory holds the pincode. Statuses: NEW_INQUIRY, CONTACTED, REGISTERED (account linked by the same email), PROPERTY_ADDED, optional SITE_VISIT_PAID / SITE_VISIT_DONE (an order for a SITE_VISIT service), QUOTED, ACCEPTED, ACTIVE, LOST. A quotation is services or one plan, priced by the server, with an optional discount and reason; accepting it creates the order at the quoted price and the case becomes ACTIVE when that order is paid. The case module catches up with orders when a case is read. Franchises see their area read-only plus notes.

Payment (maker-checker)

Staff open an unpaid order and record the money (POST /v1/admin/orders/:id/payments, multipart: amount, mode, reference, date, proof file). The amount must equal the order total. The proof is filed in the payer's vault (Payment receipts, locked). The payment waits as PROOF_SUBMITTED. A different admin approves (/approve) or rejects with a reason; the maker can only withdraw. Approval, in one transaction, marks the order PAID and starts a plan subscription. Database rules back this up: maker cannot be checker, one open and one approved payment per order, a reference used once.

Order

Customer picks services on a property (GET /v1/properties/:id/offers), previews (POST /v1/orders/preview: prices, what cannot be bought, duplicate warnings), then places it. The server re-prices every line and stores the quote with the line. Buyers for a property: its registered owner (or, for a standalone property, whoever added it) and the project owner. Status: PENDING_PAYMENT → PAID or CANCELLED, each move written to order_events.

Plan and subscription

Admins make plans: services, how many times each is done (recurrence), a discount per service, a discount for the whole plan. There is no plan price to type in. For each property the price is calculated: per service, the price of one visit (lump sum, or area x price, or the quantity set in the plan x price, minimum applied) x times, less its discount; then the plan discount. A customer buys it (POST /v1/orders/plan): an order of purpose PLAN that keeps the full breakdown, plus a subscription with entitlements copied from the plan. Paying the order starts the subscription; its end date is the last day of the period. GET /v1/properties/:id/history merges orders, plans and ownership changes for the property whoever owned it, hiding a previous owner's name and prices.

Quote

POST /v1/quotes {serviceId, propertyId, quantity?}. Checks: property active and visible to the caller, service active and bookable online, area available, a price exists (pincode price, else default, from the book live today in India). Lump sum = amount; per area = area converted to the rate's unit times the amount; per quantity checks min, max and step. Total = max(minimum, quantity × price), half-up to whole paise. Refusals are HTTP 422 with a reason.

Rules the tests enforce today

  • Another customer's property, document, KYC record or registration is 404, never 403.
  • Staff endpoints are limited by role (@Roles) and the org tree (PolicyService, roles read from the database on every call).
  • OTPs, invitation tokens and share tokens are stored hashed. Passwords are argon2id.
  • Only masked identity numbers are stored. Uploads are checked by contents.
  • One active owner per property, also as a database partial unique index.
  • Purchaser control: only the purchaser changes what they bought (property owner and project owner, both directions); the other party sees it exists but not the price; strangers get 404; ops cancel with a recorded reason. An order keeps its quote, and only the payments step can mark it PAID.
  • A price is computed only on the server. Extra price fields in a request are rejected. Money is whole paise, exact decimals, half-up.
  • Draft and retired price lists are never used. Published lists cannot be edited.
  • Every change writes an audit event.

Hierarchy, areas and job dispatch

Described by the owner on 21 Nov 2026. The organisation tree is built; provider/worker service selection and the job pool are planned (M5). Full text: docs/architecture/admin-hierarchy-and-dispatch.md.

  • Super admin (owner) → Master franchise (one city) → Franchise (an area in that city) → Service provider (contractor with workers) → Service worker.
  • Invites: admin and ops invite master franchises; a master franchise invites franchises and providers; a franchise invites providers; a provider invites workers. Each level sees and manages only its own branch.
  • Areas are pincodes, grouped into named territories. Area names are labels. A child's pincodes must lie inside its parent's.
  • Available to customers = pincode switched on AND an active, staffed provider covers it.
  • Planned dispatch: a bought service becomes a request in an open pool. Every eligible provider (covers the pincode and offers the service) sees it, as do the franchise, master franchise and ops above. The first provider to accept wins (one atomic update). Upline can nudge. The provider then assigns one of its own workers who offers the service.
  • Decided 21 Nov 2026: a franchise holds one or many pincodes and areas but never overlaps another franchise; providers choose pincodes from their franchise's list, may overlap each other, and can register under more than one franchise to serve pincodes outside their own; upline can nudge or assign directly; customer details are hidden until a provider accepts; acceptance limit 2 hours (30 minutes urgent), then escalation; a worker just gets the job and can raise "cannot attend".

Operating the console (for the team)

  1. Set up the network: Organisations → add a master franchise, then franchises and providers under it; give each a territory (pincodes). Staff → invite the person (they get a link, choose a password).
  2. Open an area: Masters → Pincodes → switch the pincode on. It only shows as available once an active, staffed provider covers it.
  3. Set up prices: Pricing → Rate types (how things are charged). Price lists → New (or copy) a draft. Service prices → for each service choose how it is charged, set a default, a minimum and any pincode prices. Publish from a date.
  4. Review identity documents: KYC review → open the scan, verify or reject with a reason.
  5. Builders and societies: Customers → open the customer → "Set up as a project owner". They then create projects and register owners. You review each registration under Owner registrations and approve it; the owner gets an email invitation.
  6. Website content: Website content and Catalogue. Saving updates the public site within seconds.
