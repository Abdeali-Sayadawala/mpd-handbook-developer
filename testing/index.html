MPD Tester Handbook

Every scenario a person can check by hand in the running app, in a sensible order, for one tester working alone. Each scenario says who you are, what to do, and exactly what you should see. Record the result as you go: it is saved in this browser, and you can download it. Open testing/index.html from the folder; nothing needs the internet.

1. How to use this handbook

0 scenarios in total. Smoke scenarios (a quick check that the whole app is alive) are marked smoke.

  1. Do Setup (section 2) once. It starts the app and builds the small "test world" that every later scenario uses.
  2. Work through the areas in the order shown on the left. Later areas rely on data made by earlier ones. Press Next scenario to do to jump to your place.
  3. For each scenario press Passed, Failed, Blocked (you could not get to it, say why) or Skipped. Add a short note. Press the same button again to clear it.
  4. When something fails, write the bug report (section 5) and carry on. A failed scenario does not stop the next one unless it says so.
  5. At the end, download the results (CSV or JSON) and send them with your bug list.
Kinds of scenario: core the main thing the feature is for. edge a boundary or unusual case. security someone who must be refused: these matter as much as the happy paths, because they protect money and private data. smoke a short pass to run before anything else after every update.
This handbook grows with the product. Every update to MPD adds the scenarios a tester needs for it (rule: CLAUDE.md and mpd-context/08-workflow.md). The version line at the bottom of this page says which update it is current for.

2. Setup (do this once, in this order)

2.1 What you need

  • The developer's machine or your own with Git, Node 22, pnpm and Docker Desktop (see workspace/NEW-MACHINE.md).
  • Chrome for most testing, plus two more isolated browser sessions (a second Chrome profile and a private window, or Firefox). The app keeps your sign-in in cookies per browser profile, so one profile can be signed in as only one person at a time. Scenarios need two or three people at once (for example a customer and a worker).
  • A phone, or Chrome's phone view (F12, then the device icon) for the phone scenarios.
  • A notes file for bug reports, and (optionally) a screen recorder.

2.3 Where the emails are

No real email is sent yet. Every email (verification codes, staff invitations, owner invitations, notifications) is printed in the terminal that runs the API (terminal 3) and by the worker (terminal 4), as to=... subject="..." followed by the text. Verification codes (6 digits) and invitation links (.../admin/accept-invite?token=..., .../owner-invite?token=...) are found there. Copy them from the terminal. Notification emails are printed by the worker within a minute.

2.6 Making time pass

Several scenarios involve waiting (reminders, acceptance limits, plan expiry). You cannot wait days, so each scenario tells you how to set the data so the condition is true now (for example a visit time within 24 hours, a document expiry in 5 days), then wait up to 10 minutes for the worker's sweep. Where a developer is needed to change a date, the scenario says so and offers the SQL or the API call.

2.7 Resetting

To start again from nothing: stop everything, run docker compose -f docker-compose.dev.yml down -v in mpd-backend (this deletes the database), then repeat 2.2. Your recorded results stay in this browser until you press Reset results.

After every update: run only the smoke scenarios first (filter by kind "smoke"), then the new scenarios for what changed, then the areas that touch it. The release notes in mpd-context/99-session-log.md say what changed.

4. Ground rules that apply to every scenario

  • Never use real people's data. Names, emails, phone numbers and documents must be invented. Use harmless sample files (a small PDF or photo you made).
  • Money is whole paise. Rs 1,000 is shown as "₹1,000". Check totals by hand.
  • Two people for money. The person who records a payment or a payout can never approve it. Always have a second account ready.
  • What you see depends on your role. If a menu item is missing for a role, that is usually correct. The scenarios say when it is not.
  • Refusals are results. "You do not have permission", "not found" and a clear message are the expected outcome of the security scenarios.
  • Write the exact text of any error message in your notes.

5. Writing a bug report

Title:     one line, what went wrong (not what you think the cause is)
Scenario:  the ID, for example JOB-07
Who/where: the account you were signed in as, the page address, the browser
Steps:     numbered, exactly what you did, with the data you typed
Expected:  what the scenario says should happen
Actual:    what happened, with the exact message text
Evidence:  a screenshot, and the lines the API terminal printed at that moment
How bad:   Blocks the work / Wrong result / Looks wrong / Wrong wording

Always include the API terminal output around the time of the failure: it names the exact error.
