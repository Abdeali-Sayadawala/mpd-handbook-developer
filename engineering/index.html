MPD Engineering Handbook

How My Property Doctors is built, for someone who knows what a server, an API and a function call are, but has not worked with Next.js, NestJS, Prisma or PostgreSQL. Read it top to bottom once, then use the left menu and the interactive diagrams as a reference. Private: for the team only. Open index.html in a browser; nothing needs the internet.

1. How to use this handbook

What it assumes, what it explains, and where the other documents fit.

It assumes you know

  • What a web server is and what an HTTP request and response are.
  • What an API is (an address you send a request to and get data back from) and what JSON is.
  • What a function is, what a class is, and what a database table is.
  • Basic git: clone, commit, push.

It explains

  • The tools we use that are specific: Next.js, NestJS, Prisma, PostgreSQL features, pg-boss, OpenAPI.
  • The architecture: which part does what, and why it is split that way.
  • For each kind of work (read data, change a status, handle money, upload a file, send a message, run on a schedule) the pattern we follow, with real file names.

Server components, client components and server actions

Server component

The default in Next.js. Drawn on the server. Can read cookies and call the API directly. Cannot hold state or react to clicks. Our page.tsx files are like this and stay tiny.

Client component

Starts with 'use client'. Drawn in the browser, can hold state (useState), run effects (useEffect) and handle clicks. Most of src/components is like this.

Server action

Starts with 'use server'. A function that a client component can call like a normal function, but which runs on the server. This is how a button press reaches the API with the visitor's session.

How the session works

  1. Login: the web app calls the API, which returns an access token (short-lived signed pass) and a refresh token (long-lived, replaced each time it is used).
  2. The web app stores both in httpOnly cookies (mpd_at, mpd_rt). httpOnly means JavaScript in the page can never read them, so a script injected into a page cannot steal the session.
  3. Each server action goes through call(), which attaches the access token. If the API answers 401, call() trades the refresh token for a new pair once and retries.
  4. The API detects a refresh token used twice (a sign of theft) and ends the session.
Hiding a menu item (the roles list in nav.ts) is cosmetic. The backend is the real permission check. Assume anyone can type any address.

One codebase, three kinds of device

The same app is used on a desktop (staff), a phone (workers and customers) and installed to the home screen (workers). Layouts adapt with Tailwind breakpoints (lg:grid and so on); the menu becomes a drawer on small screens; buttons are at least 44 px; the photo button opens the rear camera (capture="environment"). /admin/my-day is a one-column page built for a worker on a phone. There is no native app and no offline mode yet.

7. The backend (NestJS)

One Nest project, mpd-backend, with 17 modules. Click a module to see what it does, what it imports, who imports it and which tables it owns.

Arrows run from a module to the module that imports it. Modules on the left are the most basic.

Inside one module

src/modules/jobs/
  jobs.module.ts           what this module imports, provides, exports
  jobs.controller.ts       addresses (routes) and who may call them. No rules.
  jobs.service.ts          the pool, accept, assign; the rules
  job-work.service.ts      doing the work (codes, start, finish)
  job-extras.service.ts    extra work
  job-chat.service.ts      chat
  job-state.ts             the allowed status moves, in one place
  dto/                     the shapes of requests and answers

The boundary rules

  • A module never reads another module's tables. It calls that module's service. This keeps each area understandable and replaceable.
  • No import cycles. If jobs imports orders, then orders cannot import jobs. So payments never call jobs; instead JobsService.sync() looks for newly paid order lines and makes the jobs. Likewise extra-work payment is noticed by settleExtras() when the job is read.
  • Controllers route; services decide. A controller method is usually one line.

What happens to every request, in order

  1. Helmet adds security headers. CORS allows only our own web origins.
  2. Throttler counts requests (120 a minute per caller by default; stricter on sensitive routes such as codes, uploads and chat).
  3. AuthGuard (global): verifies the access token, reads the roles from it, and refuses with 401 (no or bad token) or 403 (role not listed in @Roles(...)). Routes marked @Public() skip this.
  4. ValidationPipe (global): checks the body, query and parameters against the DTO. Unknown fields are an error.
  5. Controller method runs and calls a service.
  6. The service checks ownership and rules, uses Prisma to read and write, writes audit and events, calls notify, and returns a DTO.
  7. Errors thrown (NotFoundException, ConflictException…) become HTTP answers with a plain message. Sentry records unexpected ones.

The schema is the most important file in the project. It lives in mpd-backend/prisma/schema.prisma.

The database as a second guard

Code can have bugs; the database keeps its promises. Examples we rely on:

MechanismRule it enforces
Partial unique indexOnly one open extra-work request per job. A notification dedupe key is unique per person.
CHECK constraintA rating is 1 to 5; a payment is for an order or a batch, never both nor neither; chat text is 1 to 1000 characters; an order line is a service or a plan (except extra work)
Foreign key RESTRICT on paymentsAn order with a payment cannot be deleted by accident
Unique index on payment referenceThe same bank reference cannot be recorded twice

Atomic changes: transactions and guarded updates

Two people can press buttons at the same moment. We never "read, then write" and hope. Two tools:

Transaction

Several changes that must all happen or none. Approving a payment marks the payment approved and the orders paid and starts a plan, in one prisma.$transaction.

Guarded update

updateMany({ where: { id, status: 'REQUESTED' }, data: { status: 'ACCEPTED' } }) changes a row only if it is still in the state we expect. If two providers accept at once, exactly one gets count = 1. That is how "first provider wins" works.

Changing the schema (migrations)

  1. Edit schema.prisma.
  2. Write the migration SQL by hand in prisma/migrations/<timestamp>_name/migration.sql: the CREATE TABLE, then the foreign keys, CHECK constraints and partial indexes that Prisma cannot express.
  3. Apply it: pnpm prisma migrate deploy. Then pnpm prisma generate (stop the API first on Windows).
Do not use prisma migrate dev, and never trust a generated migration. It refuses enum changes in scripts, and it generates DROP statements for our hand-made foreign keys and checks because they are not in the Prisma schema. Always read the SQL for DROP before applying it. If you must see a diff: prisma migrate diff, then keep only what you want.

9. The worker (background jobs)

What it is, why it exists, and exactly how it is wired into our code.

What is a worker?

The API answers requests: someone asks, it replies within a fraction of a second. But some work should not happen inside a request:

  • Slow things (sending an email can take seconds, and the mail server can be down).
  • Things nobody asked for right now (remind the customer a day before the visit; alert operations when no provider accepted a job).
  • Things that must be retried if they fail.

A worker is a second, separate program that runs all the time, listens to no one, and wakes up on a timetable or when a job appears in a queue. In MPD the worker is built from the same repository and the same code as the API (mpd-backend) but starts from a different file.

The API

src/main.ts, started by pnpm dev. Listens on port 4000. Does work when asked. If it is stopped, nobody can use the app.

The worker

src/worker.ts, started by pnpm dev:worker. Listens on no port. Does work on a timetable. If it is stopped, the app still works but emails are not sent and reminders pause (nothing is lost; it catches up when it starts).

How a queue works here: pg-boss

A queue is a list of jobs waiting to be done. We use pg-boss, which keeps the queue in PostgreSQL itself (in a separate schema called pgboss), so there is no extra server such as Redis to run or pay for.

  1. A schedule (a cron timetable such as * * * * * = every minute) adds a job to a named queue when it is due.
  2. The worker has registered a handler for that queue name. pg-boss gives it the job; if the handler throws, pg-boss can retry.
  3. Only one worker takes a given job, even if you run several workers.

Our small wrapper is src/common/queue/queue.service.ts: work(name, handler), schedule(name, cron), send(name, data).

The worker's three jobs today

How it is wired into the codebase

// src/worker.ts (simplified)
@Module({
  imports: [
    ConfigModule.forRoot({ isGlobal: true, validate: validateEnv }),   // same settings check as the API
    PrismaModule, AuditModule, PolicyModule, StorageModule, ScannerModule,
    JwtModule.register({ global: true }),   // these four exist only because the services we reuse ask for them
    QueueModule,                            // the pg-boss wrapper
    MessagingModule,                        // OutboxService
    RemindersModule,                        // RemindersService (and, through it, jobs, orders, vault)
  ],
  providers: [SystemJobs, OutboxJobs, ReminderJobs],
})
class WorkerModule {}

async function bootstrap() {
  const app = await NestFactory.createApplicationContext(WorkerModule);  // note: no HTTP server
  app.enableShutdownHooks();
}
  • createApplicationContext builds the dependency-injection container without an HTTP server. That is the whole difference between "an API" and "a worker" in Nest.
  • The worker reuses the API's services. It does not duplicate rules. OutboxService, JobsService.sweepReminders() and so on are the same classes the API uses. This is why the worker's module list needs PolicyModule, StorageModule, ScannerModule and a global JwtModule: those services' own dependencies ask for them. If you see "Nest can't resolve dependencies of X" when starting the worker, a module is missing from this list.
  • Each job class has onModuleInit(), which Nest calls at start-up: it registers the handler (queue.work) and the timetable (queue.schedule). Registering is idempotent, so restarts are safe.
  • The worker talks only to PostgreSQL (data and queue) and the Mailer. It never calls the API over HTTP.

Try it: the email outbox from creation to delivery

This simulator follows one email through the real design. Create an event, then let the worker tick. Turn the mail server off to watch the retries and the give-up.

Rules for anything a worker runs

  • Idempotent: running it twice must change nothing the second time. Reminders carry a dedupe key (order:<id>:24h), enforced by a database unique index, so a sweep every 10 minutes tells each person once.
  • Claim before you work: take a row with a guarded update (PENDING to SENDING) so two workers never do the same item. A row stuck in SENDING for 5 minutes (a worker died) goes back to PENDING.
  • One area failing must not stop the others: RemindersService.sweep() catches each area's errors separately.
  • Do not put rules in worker.ts. It only registers timetables and calls a service. The logic lives in the module that owns the data.
  • Never make a user action wait for the worker. The in-app notification is written immediately in the request; only the email is deferred.

Adding a new scheduled job

  1. Write the method in the owning module's service (for example sweepSomething()), idempotent, with dedupe keys.
  2. If it is a reminder, call it from RemindersService.sweep() inside its own run(...) guard.
  3. If it needs its own timetable, add a class in worker.ts like OutboxJobs and list it in providers.
  4. Write an end-to-end spec that calls your method directly (see test/reminders.e2e-spec.ts).
  5. Update this section and progress.md.
What is not built yet: reminders at a chosen local hour (for example 9 am in the reader's city); today they go out when a sweep runs. Push notifications and the real email sender (SES) come later. WhatsApp and SMS become more channels on the same outbox in M8.

10. Notifications and the outbox

How the app tells people things, and how the API and the worker share the work.

API request
A job is assigned. JobsService.assignWorker changes the job, then calls tell(job, 'worker', 'job.assigned').
NotificationsService
notify() checks the person is active, then (1) creates the in-app notification now and (2) creates an outbox email row unless they switched email off. It catches its own errors: a failed notification must never undo the assignment.
PostgreSQL
Tables notifications (the bell) and outbox (emails waiting). A unique index on (user, dedupe key) makes duplicates impossible.
Worker, every minute
OutboxService.dispatch() claims due rows, calls Mailer.send, marks SENT, or schedules a retry (2, 4, 8, 16 minutes), or FAILED after 5 tries.
Browser
The bell asks GET /v1/me/notifications/unread-count every minute and on each page change. Opening a notification marks it read.

Where the texts live

src/modules/messaging/templates.ts maps an event key (extra.needs_approval) to a title and body. Triggers only name the key and pass variables. When WhatsApp arrives in M8, a template gets another channel; the triggers do not change.

Chat is separate

Messages on a job (job_messages) belong to the jobs module. A new chat message creates one notification at a time for each other person until they open the chat (skipIfUnread), so a busy conversation does not flood the bell.

14. Testing

The tests are the safety net and the living specification. pnpm test:e2e runs about 470 end-to-end tests.

  • End-to-end means the whole API, in memory, against a real Postgres. A spec creates its own data (organisations, users with tokens, a property, a service, a price book), calls endpoints with supertest as different roles, and checks answers and stored rows.
  • Every spec cleans up after itself in afterAll. Specs run one at a time because they share one database and a global live price list.
  • Test the refusals as hard as the successes: the role that must get 403, the other customer who must get 404, the signed-out caller who must get 401, the double click that must give exactly one winner.
  • Specs call services such as outbox.dispatch() and reminders.sweep() directly instead of waiting for the worker.
  • Use a pincode and name prefix unique to your spec so runs never collide.
it('only the assigned worker can raise extra work', async () => {
  const jobId = await started();                                   // a helper that builds the situation
  await raise(jobId, 'WA2', items).expect(404);                    // another worker: not found
  for (const who of ['CUST', 'ADMA', 'OPS']) await raise(jobId, who, items).expect(403);
  await raise(jobId, 'WA1', items).expect(201);                    // the assigned worker
});

Frontend: npx tsc --noEmit and pnpm lint are the checks (plus a few unit tests). Do not run pnpm build while the dev server runs: they share the same .next folder.

Frequently asked

Why is there a separate worker instead of doing it inside the API?

A request must answer quickly and must not fail because a mail server is slow. A scheduled sweep must run even when nobody is using the app. Both needs are solved by a separate program with its own timetable. It also scales and restarts independently.

Why not Redis for the queue?

Postgres already holds the data and pg-boss is enough for our volume. It saves a server to run and pay for at launch. It can be replaced later because only queue.service.ts knows about it.

Why does the browser never call the API directly?

The tokens live in httpOnly cookies on the web app's server. Scripts in the page cannot read them, so an injected script cannot steal a session, and the API address is not exposed to visitors.

Why are migrations written by hand?

Generated ones drop our foreign keys and checks, which Prisma does not model. Hand-writing keeps the database rules, which are our last line of defence.

Why are there so many tests for refusals?

A system that handles money and private property data is judged by what it refuses. Each role is tested for what it must not do.

Why is a customer's job not found (404) instead of forbidden (403)?

403 confirms the thing exists. 404 reveals nothing.

Why is the worker's name only the first name to customers in chat?

Privacy: customers do not need a worker's full identity, and phone numbers are never shown in chat.

Can a native app be added later?

Yes. It would use the same API through the same contract (openapi.json); mpd-mobile is the scaffold. We chose the installable web app first because it covers the worker's needs and is one product to keep.
